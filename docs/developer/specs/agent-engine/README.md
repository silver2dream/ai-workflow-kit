# Agent Engine

> **狀態：已核可（2026-11-23），分階段實作中。** 架構與六個決定由專案擁有者核可（見下方「已定的決定」）。各階段完成時，在下方「進度」表更新，並在 `tasks.md` 勾選。

把 `awkit run` 從「一個 LLM 主控照著 `analyze-next` 一次做一張」改成**確定性的 Go engine**：依每張工單的狀態，把工作派給有各自設定與限制的 agent，多條線平行做、合併一次一張；每一個 agent 的輸入、執行與輸出都經過分層的 guardrail；人隨時看得到每條線、下得了指令，明顯的高風險由人核可。

- [`requirements.md`](requirements.md)：要做到什麼、為什麼、怎樣才算做到
- [`design.md`](design.md)：怎麼做，含架構、資料流、狀態機、guardrail、容器隔離與遷移
- [`tasks.md`](tasks.md)：分階段的工作單位與相依

## 為什麼

2026-11-23 的架構審查結論（細節見 `design.md` §1）：

1. **主控不做判斷。** 下一步由 `awkit analyze-next`（Go）決定，主控只是轉達，卻造成三個問題：一次只能做一張、整個執行綁死在 Claude Code 上、審查與解衝突寄居在主控的 session 裡，權限分不開。
2. **一次只做一張。** `internal/analyzer/analyzer.go` 只要有一張工單帶 `in-progress` 就不派下一張，`awkit dispatch-worker` 又是同步等執行者做完。
3. **guardrail 不完整，而且有些只寫在 prompt。** 外來內容直接接進 prompt；主控與審查技術上都能直接合併 PR；Claude 執行者沒有自己的權限設定、沒有隔離；沒有範圍檢查、注入偵測、對外文字掃描、議會出處檢查；教訓不經隔離就生效。
4. **一張工單需要人，整輪就停。** `analyze-next` 看到任何一張 `worker-failed` 或 `needs-human-review` 就結束整輪。

## 已定的決定

| # | 問題 | 決定 |
|---|---|---|
| D1 | LLM 主控 | 拿掉，由 Go engine 取代。LLM 在編排層只做兩件有邊界的事：分診沒見過的錯誤（從固定處置中選一個）、把白話指令翻成結構化指令（先給人確認）。兩者都不能直接執行任何動作 |
| D2 | 平行 | 上限可以設定；依工單的依賴關係自動排，人可以再調整（優先、固定一組一起做、暫停某條線） |
| D3 | 工單 | 議會產出的工單多宣告「會動到的路徑」與「風險等級」，供範圍檢查、平行避撞與高風險關卡使用 |
| D4 | 人的關卡 | 只有 guardrail 觸發才停那一條線，其他線照跑，合併不等人；**明顯的高風險要人核可** |
| D5 | 注入偵測 | 第一層是確定性規則（regex、隱藏字元、結構特徵），所有外來內容都過；第二層是可替換的分類器（本機小型模型或小模型判讀），不需要 GPU；預設值在 P4 以含中文的紅隊語料評估後決定（`design.md` §9.7）。真正的保證是第三層：工具與容器的限制 |
| D6 | 隔離 | 容器模式：每個 agent 在容器裡跑，只掛自己的 worktree，對外連線只能經過白名單 proxy |

## 階段

| 階段 | 內容 | 可單獨上線的成果 |
|---|---|---|
| P0 | 在現有架構上先補安全 | 外來內容標來源並包成資料、規則層注入偵測、指令政策 hook、執行者有自己的權限設定、清環境變數、對外文字掃描、教訓篩檢 |
| P1 | Engine 取代 LLM 主控 | `awkit run` 由 engine 驅動，行為與現在相同（一次一張），審查與解衝突成為獨立程序；以影子模式比對後切換 |
| P2 | 平行與人的控制 | 工單 schema v2、多條線、依賴與路徑避撞的排程、合併佇列、線各自失敗、指令通道、高風險關卡 |
| P3 | 容器隔離 | 每個 agent 與驗證指令都在容器裡跑，對外連線走白名單 |
| P4 | 完整 guardrail pipeline | 分類器層注入偵測、議會出處檢查、內容審核、教訓隔離、可設定的政策、判定稽核 |
| P5 | 多廠商與 LLM 輔助角色 | provider 介面、更多 coding agent 轉接、分診 agent、白話指令翻譯 |

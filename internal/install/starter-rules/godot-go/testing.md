# Testing Rules

Scope：`backend/`（Go）與 `frontend/`（C#、xUnit）。這是專案自己的規則檔，`awkit init` 只寫下起始內容，之後由專案維護。

## 1) 每個變更都帶測試

- 新功能有對應的測試；改了行為就改或加測試；修 bug 先寫一個會失敗的測試，再修。
- 每個行為至少涵蓋：正常路徑、無效輸入、邊界（空、零、上限）、失敗路徑（依賴出錯、逾時）。
- 票的驗收條件，每一條都要對得到一個實際跑過的測試；審查會拿測試名稱與測試輸出來核對。

## 2) 三道關卡

新增測試前過這三關；審視既有測試也用同一個標準。

1. **看得到的行為**：斷言對外的介面（回傳值、回應、ViewModel 的狀態），不探內部欄位。要驗內部，就在那一層寫單元測試。
2. **真實的情境**：流程對得上實際的使用方式。純粹防止退步的測試可以有，名稱或註解要說明防的是哪個 bug。只有違反正式環境的不變量才會過的測試，錯的是測試。
3. **斷言的強度**：驗業務上的意思，不是 `err == nil`、`len(x) > 0`、`NotNull`。名字說「冪等」就驗第二次呼叫沒有效果；說「擋下」就驗真的被擋。

## 3) Backend（Go）

- 測試檔與被測程式放在同一個目錄（`foo_test.go`）；多組輸入用 table-driven。
- 依賴用手寫的 fake（實作同一個介面），不引入 mock 產生器。
- 測試之間不共用狀態、不依賴執行順序；用 `t.TempDir()`、`t.Setenv()`，不留下檔案。
- 時間、亂數、網路由外面傳進來，測試才固定得住它們。

## 4) Frontend（C#）

- 規則與狀態在 `src/Game.Core`，用 xUnit 測（`tests/Game.Core.Tests`），不需要 Godot。
- 要引擎才測得到的部分（場景、輸入）保持很薄，邏輯移進 Core 測。
- 測試方法的名稱說出行為：`Increment_FromZero_ReturnsOne`。

## 5) 失敗的測試

- 測試失敗，先查是不是實作錯了：修實作，不是改測試讓它過。測試本身錯了才改測試，並在 PR 裡說明。
- 不跳過、不註解掉失敗的測試來交差。
